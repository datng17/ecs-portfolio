Latency interpretation
----------------------
The latency SLO is measured at the origin: the portfolio-dev-alb-latency-p95 alarm uses ALB
TargetResponseTime p95 > 0.3 s. On that definition the run passes with ~1 ms, about 290x headroom.

The client-side p95 fails because the load generator's own downlink was the bottleneck, not the service:
- The run received 307 MB in ~129 s = 2.4 MB/s (~19 Mbit/s) sustained. Each page view downloads ~460 KB,
  mostly the 442 KB JS bundle, which is a Cloudflare HIT and never reaches AWS.
- A single unloaded download of the JS bundle from the same machine right after the run: 315 KB/s, 1.40 s.
- /healthz returns a few bytes and takes ~1 ms at the origin, yet its client p95 is 9.16 s. It is queued
  behind the bundle downloads on the same saturated link.
- The minimum durations match the unloaded baseline: 96 ms for an edge HIT, 288 ms for an origin
  request (VN -> Cloudflare SIN -> ALB Sydney round trip).
To measure client-side p95 against 300 ms, run k6 from a host with more bandwidth that is close to
Sydney (e.g. an EC2 instance or k6 Cloud in ap-southeast-2). That is out of scope for Task 13.
